## 我是谁

一个把「测试」当成**工程问题**而不只是"点点看"的在校生。

我做过三件不同的事，但它们共用同一个思路：**先把系统拆成可验证的边界，再让机器去守这些边界。**

- 给一个真实上线的第三方站点搭了一套 **pytest + Page Object 自动化测试框架**，
  30 条用例、单轮通过率 100%，并把"脚本"重构成"框架"；
- 写了一个 Selenium 爬虫抓 250 × 10 字段的数据，然后花更多时间在
  **"怎么证明这 2500 个字段是对的"** 上——21 条数据质量断言 + 12 条解析单元测试；
- 在 Coze 平台上编排了一个 **40+ 节点的 AI 工作流**，并给它设计了 16 条测试用例
  （其中 12 条如实标注为"待执行"）。

> 我倾向于把话说准：已经跑通的写"通过"，没验证的写"待执行"。
> 测试报告里最没价值的一句话，就是全都画勾。

## 项目

### 🧪 [doonsec-web-auto-test](https://github.com/lyhua1435-cmd/doonsec-web-auto-test) · Web 自动化测试框架

**pytest + Selenium + Page Object** ｜ 面向真实上线站点（70 万+ 安全文章全文检索平台）

| | |
|---|---|
| 用例规模 | 30 条手工设计 + 5 条参数化（待回归） |
| 执行结果 | 已执行 30 条，**30 passed / 0 failed** |
| 核心改造 | 脚本 → 框架：定位器收敛、显式等待、session 级复用、失败自动截图 |
| 设计文档 | 等价类 / 边界值 / 场景法 / 错误推测 四类方法的具体落地 |

**最能代表我的一段**：`test_23` 这条用例不是照着需求写的，而是**从一个真实缺陷
反推出来的**——分类点击后内容区曾出现链接塌陷，所以这条用例断言的不是"点击成功"，
而是"点击后页面结构没被破坏"。这是自动化测试相对手工测试最值钱的地方：**一次发现，永久回归。**

### 🕷 [douban-top250-selenium](https://github.com/lyhua1435-cmd/douban-top250-selenium) · 爬虫 + 三层测试体系

**Selenium 4 + pytest** ｜ 250 部电影 × 10 字段结构化数据，含可视化分析

| | |
|---|---|
| 数据成果 | 250 条，评分区间 8.4–9.7，覆盖 1931–2023 共 10 个年代 |
| 测试体系 | 单元 12 条 + 数据质量 21 条 + 端到端 3 条，前两层 **0.07 秒**跑完可进 CI |
| 迭代沉淀 | v0 → v0.3 四个版本，每次改动的"为什么"都写进了 `docs/迭代记录.md` |

**最能代表我的一段**：数据质量用例没有写成 `assert 缺失数 == 0`。
250 条里有 15 条主演为空——那是动画、纪录片本身就不返回该字段，
**属上游数据缺失，不是爬虫 bug**。所以用的是**缺失率门禁**（主演 ≤ 8%、国家/类型 ≤ 2%）：
字段大面积丢失时立刻报警，几条固有缺失则不打扰。

这是我在写用例时最常提醒自己的一件事：**一条会常年红灯的用例，等于没有用例。**

### 🎵 [coze-music-video-agent](https://github.com/lyhua1435-cmd/coze-music-video-agent) · AI 音乐视频生成智能体

**Coze 工作流编排** ｜ 输入歌名 → 自动生成带动态歌词的剪映草稿

| | |
|---|---|
| 工作流规模 | 14 个阶段 / 40+ 节点 |
| 核心难点 | LRC 时间轴 → 字幕区间（用下一个起点当自己终点）、歌词 → 图像提示词的两段式转换 |
| 测试情况 | 4 条主链路已执行通过，**12 条边界/异常/输出质量用例已设计未执行** |

**最能代表我的一段**：这个项目最难的测试问题不是"能不能跑通"，
而是 **"少了一层素材也不会报错"**。40 多个节点里，字幕数组为空时草稿照样生成成功，
只是没有歌词。所以我在文档里提的改进方案是：保存草稿前加一个「产出物自检」节点，
检查关键图层数量，不满足就返回明确错误——**别让"成功"掩盖了"不完整"。**

## 我在测试上的几个观点

**1. 用例数量不是指标，"能长期活下去的用例"才是。**
一条每天都要人工判断"这个红灯是不是误报"的用例，比没有这条用例更糟。

**2. 不稳定逻辑必须隔离在页面对象层。**
用例层一旦出现 `if`、重试、`sleep`，这条用例的可信度就已经下降了。
它到底是在验证功能，还是在验证"这次运气好不好"，说不清了。

**3. 别把上游的问题当成自己的 bug 去修。**
主演字段缺失是豆瓣不返回，不是爬虫抓错。硬修只会写出越来越复杂的兜底逻辑，
最后还是修不对——正确做法是把它变成一条有阈值的断言。

**4. 未执行的用例不能标"通过"。**
测试报告里最危险的不是红色，是假的绿色。
